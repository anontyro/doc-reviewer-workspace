# LLM Review Workspace — Product Requirements Document

**Status:** Discovery complete; implementation planning baseline  
**Revision:** PRD 1.0 · 2026-11-06  
**Product working title:** LLM Review Workspace (placeholder; not a branding decision)  
**Owner:** Solo developer, AI-assisted  
**Initial platform:** macOS  
**Implementation strategy:** Tauri 2 + Rust + React/TypeScript  
**Release strategy:** Incremental milestones, flexible cadence, Semantic Versioning

> **Intent:** A small, fast, local-first Mac utility for reviewing documents created with an LLM, attaching precise human feedback, exporting reliably grounded instructions back to the LLM, and managing successive versions inside portable projects. It is **not** a general-purpose office suite or an autonomous AI rewriting agent.

## 0. Decision taxonomy

- **Confirmed:** Expressly selected during discovery. Must be reflected in design.
- **Recommended:** Product or technical recommendation offered during discovery; validate before treating as binding.
- **Deferred:** Explicitly not needed for initial releases; retain on roadmap only.
- **Open:** Requires technical investigation or a subsequent decision.

Implementation agents **MUST NOT** silently turn recommendations into confirmed scope, expand deferred features into MVP, or improvise destructive file operations.

## 1. Executive summary

### 1.1 Problem

LLM-produced specifications, plans, research documents, and designs are frequently exported for careful human review. Current workflows scatter feedback across notes, chat messages, inline edits, and comments. Reconstructing those comments as unambiguous LLM instructions is slow and error-prone. Existing editors often focus on authoring or human collaboration rather than machine-readable feedback handoffs.

### 1.2 Proposed solution

A native-feeling, local-first desktop application with:

1. User-owned named project folders that group related documents.
2. Rendered reading and annotation of Markdown; source-based Markdown editing.
3. Read-only, text-selectable PDF annotation, introduced after the complete Markdown loop.
4. Notion-inspired inline/contextual review actions and a unified sidebar.
5. Anchors capturing the target passage, context, location, document identity, and document version.
6. Deterministic, selectable feedback export as a copyable Markdown prompt or portable review package, with preview before handoff.
7. Explicit import of LLM-revised files as document versions, with persisted review rounds and export snapshots.

### 1.3 Product positioning

**Confirmed primary user:** The developer building the utility, using it personally for AI-assisted document iteration. Potential later audiences: developers, technical writers, product managers/designers, and AI power users. A public beta is optional and downstream of demonstrated personal value.

### 1.4 Non-goals for MVP

- Cloud accounts, collaboration, server backend, subscriptions, analytics collection, or remote APIs.
- Built-in LLM calls or automatic rewriting.
- WYSIWYG rich-text editing, PDF content editing, PDF-embedded annotations, or OCR.
- DOCX, CSV, XLSX handling in the Markdown-first release.
- Automatic semantic reconciliation of whether a model followed instructions.
- Live folder watching and automatic version matching.

## 2. Goals, outcomes, and principles

### 2.1 Primary user job

> Given a document generated by an LLM, I want to read it, mark specific content with corrections or decisions, and export a precise package of those instructions so that the LLM can revise the document without losing context or modifying unrelated passages.

### 2.2 Success scorecard — confirmed target directions

| Measure | Initial target | Measurement protocol | Notes |
|---|---:|---|---|
| Feedback preparation time | ≥30% less time | Time 5–10 equivalent manual vs application review-preparation tasks | Establish baseline first; not a demonstrated result |
| Target anchoring correctness | ≥95% | Count comments whose target resolves to intended passage in *unchanged supported documents* | Test repeated text, headings, tables, lists |
| Real use | ≥1 genuine workflow per week | Lightweight private manual log | No telemetry SDK |
| Data loss | 0 incidents | Regression tests, controlled failure/recovery tests, real usage log | Release-blocking defect |
| Completed iteration loops | Monitor count and completion | Review → export → LLM revision → reimport → subsequent review | Diagnostic metric, no invented threshold |

**Recommended quality distinction:** Verify *export correctness* independently from *LLM compliance*. LLM behavior is external to the utility.

### 2.3 Product principles

- **Review first:** Feedback handoff is the hero feature, not editing breadth.
- **Fast and low-friction:** Keyboard-first workflow; optional, contextual menus; short path from selection to saved comment.
- **Local-first:** MVP works without a network connection.
- **File ownership:** Project data remains in normal, user-controlled folders.
- **Lossless inputs:** Reading or switching views must not rewrite source documents.
- **Deterministic exports:** Preserve literal user feedback; never silently paraphrase or merge comments.
- **Explicit changes:** Replacing documents and creating versions requires clear user intent.
- **Progressive breadth:** Excellent Markdown iteration before many imperfect file adapters.
- **Incremental milestones:** Deliver complete vertical slices; don't tie releases to calendar dates.

## 4. Core journeys and workflows

### 4.1 Quick single-document review

1. User launches app and opens or drops a `.md` file without first creating a project (**confirmed preferred direction from UX discussion; recommended Quick Open implementation**).
2. Rendered view opens by default; source toggle available.
3. User selects text. Floating toolbar offers Comment, Replace, Remove, Approve; expanded actions include Expand and Question.
4. User writes freeform feedback; app stores original quote, surrounding context, hierarchy, and version reference automatically.
5. User opens review panel to inspect, update, resolve, or exclude comments from a particular export.
6. User opens export preview, sees exactly what will be transmitted, copies a generated Markdown prompt.
7. User pastes it into existing LLM conversation along with appropriate original source context.

### 4.2 Project-based review

1. Create or open a named project represented by a normal directory.
2. Add multiple document files; app copies imports to project by default (**confirmed**).
3. Open tabs and review each document; annotations persist per document/version.
4. Choose one document, selected documents, or the entire project for export.
5. Choose comments/actions and inspect preview; export a portable bundle or copy relevant instructions.

### 4.3 Revision cycle

1. Complete a review and export; record export snapshot containing exact instructions and included document-version IDs.
2. User obtains an edited Markdown file from external LLM.
3. Explicitly select **Import as New Version** for the existing logical document.
4. App preserves previous bytes/version, establishes new version, and starts a new review round.
5. Review history remains available. Manual reconciliation and diffs are later enhancements.

### 4.4 Reading, source editing, and reviewing

- **Reading mode:** Rendered Markdown; review highlights and unobtrusive markers.
- **Review mode:** Document with right-hand review sidebar and contextual annotation tools.
- **Editing mode:** Raw Markdown editor with formatting shortcuts, syntax highlighting, find, undo/redo, autosave safeguards.
- Modes are panel/layout configurations, not different source formats. Source is canonical.
- PDF reading/review uses format-specific renderer with shared review semantics; no PDF content edits.

## 5. Feature specification and priorities

Priority vocabulary: **P0** = release-blocking for named milestone; **P1** = desired for that milestone; **P2** = later. All milestones below are proposed implementation gates consistent with confirmed progressive release strategy.

### 5.1 Vertical-slice prototype (P0)

- Open existing Markdown file.
- Render Markdown without modifying underlying bytes.
- Select a passage, attach a freeform comment.
- Persist a comment and retrieve it when reopening.
- Generate deterministic Markdown feedback instruction containing quote/context/section.
- Copy feedback to clipboard.
- Test the whole cycle using a real LLM chat (manual handoff).

**Gate:** A source document can be reviewed and its comments returned accurately to a model; no comments lost on app restart.

### 5.2 Personal alpha (P0)

- Named user-controlled project folders; create, open, rename, delete with safe prompts.
- Local library index of known projects (proposed SQLite; project data stays in folders).
- Add documents via picker/drag-and-drop, copying into project folder by default.
- Quick Open outside a project.
- Project file explorer and tabs; collapsible left and right sidebars.
- Source Markdown editing, syntax highlighting, basic formatting keyboard shortcuts, rendered/source toggle, basic search.
- Notion-like selection toolbar, optional action categorization, comment list, edit, resolve/reopen.
- Anchors with quote/context/heading path and revision binding.
- Autosave plus crash-safe writes, restore after restart, external modification protection.

**Gate:** User can resume interrupted reviews and manage a real project safely.

### 5.3 Usable v0.1 (P0)

- Structured `Copy Feedback` and `Export Review Package` actions.
- Export scope: single document, selected documents, complete project; include/exclude annotations.
- Export preview before copy/save; optionally warn on ambiguous/unresolved references.
- Immutable review round and export snapshots.
- Import revised Markdown as an explicit new version; view prior snapshots and revert/copy safely.
- Portable project structure and documented export manifest.
- Robust tests for repeated text, quoted headings, source edits, reopens, and multiple exports.

**Gate:** At least one reliable two-version LLM review cycle; no data loss or misleadingly confident anchors in representative tests.

### 5.4 PDF beta (P0 for this milestone, not v0.1)

- PDF rendering, paging and zoom, via PDF.js or validated alternative.
- Text selection, text-range comments, page number and exact quote capture.
- Persist highlights and comment navigation.
- Export PDF feedback with page/quote/reference; preserve original PDF unchanged.
- Fail gracefully for PDFs with no selectable text; OCR excluded.
- Flag low-confidence extraction and ambiguous anchors.

**Gate:** Both Markdown and ordinary text-based PDFs can be reviewed and exported reliably. No claim of support for scanned PDFs.

### 5.5 Later (deferred)

- Markdown visual diff and manual review reconciliation.
- DOCX render/select/annotate, then potentially basic editing after fidelity spike.
- CSV/XLSX table/cell-level review; formula semantics and location validation.
- Optional AI-assisted conflict resolution, comment grouping and change verification, only with explicit opt-in.
- More advanced project search/organization, prompt templates, OCR, visual PDF area annotations, public packaging, cross-platform support.

## 6. Review interaction requirements

### 6.1 Freeform-first interaction

1. Select text in rendered document.
2. Open floating toolbar near selection, without obscuring selected content.
3. Default action **Comment**; action types **Comment**, **Replace**, **Remove**, **Expand**, **Question**, **Approve**.
4. Enter a freeform note, with replacement-text input for Replace if needed.
5. Save via keyboard shortcut and with pointer, preserving selection and focus.
6. Highlight target and show sidebar comment; clicking comment navigates to target.

**Recommended keyboard shortcuts (not confirmed key assignments):** `Cmd+Shift+M` add comment; `Cmd+Enter` save; `Esc` dismiss; `Cmd+F` find; normal `Cmd+B`/`Cmd+I` for source formatting. Audit shortcuts for conflicts with macOS/Tauri.

### 6.2 Annotation states

- `open`, `resolved`, `superseded` (recommended data states).
- Export inclusion is **not** the same as annotation status: excluded comments remain saved.
- For an `Approve` action, export instruction should explicitly preserve targeted content.
- No silent automatic reanchoring or resolution when source changes.

### 6.3 Anchoring strategies

**Markdown:** Logical document ID, immutable document-version ID, AST/heading path when available, exact selected text, prefix and suffix context, source range as derived helper, internal ID, hash of source snapshot. Line numbers are generated against the exact exported version; never sole identity.

**PDF:** PDF source version/hash, page index/number, selected text, text-layer offsets/rectangles where available, surrounding context. Warn if extraction lacks confidence; never manufacture a precise quote.

**Anchor states:** `resolved`, `ambiguous`, `orphaned` as recommended values. When ambiguous, export must disclose uncertainty and preserve contextual evidence rather than make a false certainty claim.

### 6.4 Conflicting and overlapping annotations

MVP does not automatically merge them. Export each instruction with unique ID and target. If overlapping instructions conflict, preserve both, emit optional warning, and request model/user resolution rather than choosing one silently.

## 7. LLM export contract

### 7.1 Required export behaviors

- Deterministic; no model required.
- Exact user comment preserved verbatim in a `user_instruction` field.
- Group by project/document/section in Markdown for readability.
- Include explicit preservation rule: only change specified content; preserve unrelated sections.
- Include instructions to identify unresolvable/conflicting changes rather than hallucinate.
- Include documented source version/hash or fingerprint.
- Include annotations selected for this export only; don't delete excluded annotations.
- Before exporting, preview document selection, action count, generated prompt, warning list, output size and optional estimated tokens.
- Support clipboard Markdown prompt and portable file bundle.
- Distinguish **copy prompt** (assumes model has source or source is pasted/uploaded) from **self-contained package** (includes sources).

### 7.2 Sample human-readable feedback Markdown

```markdown
# Review Instructions
Project: Colony Management Game
Export: EXP-2026-11-06-001

## Instructions
Apply only the requested revisions to the included source versions.
Preserve unmentioned sections. Preserve exact approved passages.
If any target is ambiguous or instructions conflict, report the issue.

### DOC-001 — product-requirements.md (version 2)
#### REV-014 — REPLACE
Section: 4.2 > Authentication
Source lines (version 2): 128–134
Target quote: "The system must use an external identity broker."
Context before: "Authentication should be straightforward."
User instruction (verbatim): "Remove the external dependency; local auth is enough."

#### REV-015 — APPROVE
Section: 5.1 > Storage
Target quote: "All document storage is local-first."
User instruction (verbatim): "Keep this as is."
```

```json
{
  "schema_version": "1.0.0",
  "export_id": "exp_001",
  "project_id": "project_001",
  "created_at": "2026-11-06T00:00:00Z",
  "documents": [
    {
      "document_id": "doc_001",
      "version_id": "ver_002",
      "relative_path": "product-requirements.md",
      "sha256": "<actual-digest-from-export>",
      "annotations": [
        {
          "id": "rev_014",
          "action": "replace",
          "status": "open",
          "user_instruction": "Remove the external dependency; local auth is enough.",
          "target": {
            "type": "text_quote",
            "exact": "The system must use an external identity broker.",
            "prefix": "Authentication should be straightforward.",
            "suffix": "",
            "heading_path": ["Architecture", "Authentication"],
            "source_line_start": 128,
            "source_line_end": 134,
            "confidence": "resolved"
          }
        }
      ]
    }
  ]
}
```

`<actual-digest-from-export>` is illustrative, not a real digest. Numeric line references are illustrative. Define JSON Schema and validation rules before implementation. A real export MUST include correct values only.

### 7.4 Portable export package (recommended)

```text
review-package.zip
├── manifest.json
├── instructions.md
├── sources/
│   ├── product-requirements.md
│   └── architecture.md
└── metadata/
    └── annotations.json
```

For partial export, include only selected document versions and comments; clearly disclose scope in manifest. Preserve original source bytes. Archive naming and exact structure remain open implementation decisions.

### 7.5 Security/privacy

Files can include secrets or sensitive material; no automatic network transmissions. Preview lists file names and size before export. Treat comments and document content as untrusted when displayed; Markdown renderer must sanitize any HTML and links appropriately. Prevent ZIP path traversal on import; validate manifests and size limits. Protect Tauri file-system permissions, restrict command surface, and avoid arbitrary shell execution.

## 8. Project files, persistence and version model

### 8.1 Confirmed ownership model

Projects are user-controlled ordinary folders. Imported documents are copied to project by default; user retains ownership. Project metadata and snapshots live in a hidden application subdirectory. A separate lightweight local library index of recently opened projects is recommended, not a replacement for portable project data.

### 8.2 Proposed folder shape

```text
my-project/
├── product-requirements.md
├── architecture.md
├── concept.pdf
└── .review-workspace/
    ├── project.json
    ├── annotations/
    ├── versions/
    └── exports/
```

Names/layout are provisional. Don't require all project files to be under this exact schema if a migration is needed. Track explicitly added documents rather than recursively indexing every file. Ignoring `.review-workspace/` in external tooling should be documented.

### 8.3 Conceptual data entities

| Entity | Essential fields | Relationships |
|---|---|---|
| Project | id, name, root_path, created_at, updated_at | many Documents |
| Document | id, project_id, relative_path, format, active_version_id | many Versions |
| DocumentVersion | id, document_id, version_number, content_hash, snapshot_path, created_at, origin | many ReviewRounds |
| ReviewRound | id, document_version_id, state, created_at, completed_at | many Annotations |
| Annotation | id, round_id, action_type, text, replacement_text?, anchor, status, timestamps | belongs to versioned round |
| ExportSnapshot | id, created_at, format, document_version_refs, annotation_ids, payload_hash, relative_output_path | captures exact handoff |
| LibraryEntry | project_id, last_opened_at, local_index_path | local-only index; rebuildable |

**Rule:** A document is a logical identity; a version is an immutable source snapshot; a review round collects feedback for a version; an export snapshot is an immutable record of a selected subset. Working edits do not each create a new version.

### 8.4 Persistence behaviors

- Use atomic file writes (write temporary file, sync/rename as appropriate) and crash recovery tests.
- Keep immutable snapshots before destructive replacements.
- Reimport revised file only after user explicitly confirms target logical document.
- Compare on-disk source fingerprint before save; if changed externally, block silent overwrite and present conflict resolution.
- Support safe project deletion without silently removing unrelated user files; choice between removing library entry and deleting contents requires explicit design.
- Avoid schema migration that destroys historical annotations; back up and test migration.
- SQLite recommended for local library; project metadata format may be JSON files, SQLite inside project, or hybrid—validate portability and atomicity in technical spike.

## 11. Testing and quality gates

### 11.1 Test fixture matrix

- Markdown: small/long, repeated phrases, duplicate headings, nested lists, tables, code fences, links, Unicode, CRLF/LF, edited after comment, renamed file.
- PDF: selectable text, columns, tables, unusual fonts, zero text layer, encrypted/corrupt PDF, rotated page, zoom and page navigation.
- Workspace: external file changed, missing file, project moved, insufficient permission, empty or very large projects.
- Exports: multiple docs, selected/excluded comments, quote escaping, conflicts, orphaned anchors, no comments, long prompts, deterministic ordering.

### 11.2 Acceptance tests (Given/When/Then)

**AT-01 Anchor persistence:** Given a Markdown passage selected in rendered view, when the user adds a comment, closes and reopens the project, then the same target remains highlighted and its comment appears with the original quote and source version.

**AT-02 No destructive render:** Given a Markdown file with specific whitespace and line endings, when the user toggles preview/source without changing content, then the file bytes remain unchanged.

**AT-03 Export exactness:** Given selected annotations across two documents, when exporting, then every chosen instruction appears verbatim, excluded comments do not appear, and all reference the correct source versions.

**AT-04 Export preview:** Given an export selection, when preview opens, then the text shown matches the emitted prompt byte-for-byte apart from documented packaging metadata.

**AT-05 Version reimport:** Given a completed review on version 1, when the user explicitly imports LLM revision version 2, then version 1 and its review/export snapshots remain retrievable.

**AT-06 External edits:** Given a file modified in another application after opening, when save is requested, then the utility does not silently overwrite the external edit.

**AT-07 Ambiguity:** Given an anchor matching multiple passages with no uniquely resolvable context, when exporting, then the output flags ambiguity rather than falsely selecting one target.

**AT-08 Package:** Given a selected two-document export, when package is unpacked, then manifest hashes validate and only the selected source versions and relevant annotations are included.

**AT-09 Offline:** Given network disconnected, when opening, annotating, exporting and reimporting supported Markdown, then the full flow works.

**AT-10 PDF:** Given selectable text-based PDF, when selecting and commenting on page 4, then the export contains correct quoted text and page reference while the PDF source remains unmodified.

### 11.3 Release blockers

- Source file corruption or lost comments.
- Incorrect source version used in export.
- Exported text silently differs from user-authored comment.
- Silent destructive overwrite of externally modified document.
- Dangerous archive paths or untrusted HTML/script injection.

## 13. Release management and Semantic Versioning

### 13.1 Confirmed cadence

**Hybrid milestone-based development:** Release features when coherent, with small fixes in between; no fixed dates, no mandatory monthly cadence. Public release process is deferred. Possible later shift toward A (feature-driven) or B (monthly) only once core alpha workflow is established.

### 13.2 Confirmed versioning preference

Use **Semantic Versioning** (`MAJOR.MINOR.PATCH`), with documented pre-1.0 milestone versions.

**Practical interpretation for this project:**

- `0.1.0` = first complete personal Markdown review iteration workflow.
- `0.1.1` = backward-compatible bug fix/quality patch.
- `0.2.0` = PDF review milestone (target, subject to quality gate).
- `0.3.0` = visual diff/manual reconciliation milestone.
- `0.4.0` = DOCX review milestone.
- `0.5.0` = CSV/XLSX review milestone.
- `0.6.0` = optional AI assistance milestone.
- `1.0.0` = stable release once API, project format and quality expectations are mature.

**Important SemVer nuance:** Pre-`1.0.0`, public API stability is not guaranteed by SemVer, and `0.x` versions may include breaking changes. However, this application must independently guarantee **explicit and tested migrations for persisted project files**, backups before incompatible migration, and a way to identify project schema versions. Schema version is separate from app version; do not assume `schema_version == app_version`.

Recommended development tags include `0.1.0-alpha.1`, `0.1.0-beta.1`, then stable `0.1.0`; patch tags for fixes. Maintain changelog, release checklist, feature flags only as needed; tag Git commits at milestone acceptance. Keep detailed internal build history even before public distribution.

1. Confirm scope for the milestone.
2. Complete vertical-slice acceptance checks and regression tests.
3. Confirm data safety and export correctness.
4. Update changelog and project/manifest schema documentation.

## 17. Definition of product completion

Discovery is complete when this PRD reflects all 20 confirmed answers. Implementation is *not* complete until the personal v0.1 user can repeatedly: open/import Markdown → review/annotate → selectively preview/export precise instructions → obtain revised document externally → import it explicitly as new version → resume review, with persistent data and no unintended changes.

**PRD governance:** Treat this as a controlled baseline. If an implementation task reveals a conflicting assumption, document the decision in a short ADR and update the PRD with a revision note rather than silently changing requirements.
